# SecRelay-Relay 设计（v0.1）

> 配套：SecRelay 主仓库 `docs/需求分析.md`（§3.1 连接方式、§6.3 传输与媒体栈）、
> `docs/research/transport-media.md`（传输选型与中继成本模型）。

---

## 1. 定位与边界

**一句话**：SecRelay-Relay 是"让打洞失败的设备也能连上"的**无状态、零知识、无账号**的转发与协调服务。

| 本服务提供 | 本服务不提供 |
|---|---|
| 信令协调（交换候选地址、协调打洞） | 账号、登录、用户资料 |
| STUN 反射（获取公网映射地址） | **解密任何内容**（零知识） |
| 打洞失败时的密文中继（UDP / TCP-443） | 离线消息暂存（独立组件） |
| 短期 ICE 凭据签发 | 用户数据持久化 |
| 配额、限速、滥用防护 | 客户端 UI |
| 中继占比等 KPI 埋点 | 媒体编解码 |

### 已定的产品决策

- **不做账号验证**：任何人可以连，中继不校验 token、不关心是否登录过 SECTL-auth。
- **P2P 优先**：中继是**兜底路径**，不是默认路径。
- **零知识**：中继只转发密文。

## 2. 为什么不自研 TURN

这是本仓库最重要的一个技术判断：**不要把 TURN 协议重新实现一遍**。

| 方案 | 结论 |
|---|---|
| 复用 **coturn** | ✅ 采用。成熟、久经考验，原生支持 TCP/443 回退（穿透企业防火墙的关键）、UDP 端口池、TLS/DTLS、长期/短期凭据 |
| 自研 TURN | ❌ 不采用。纯属重造轮子，且 RFC 8656 的边界情况极多 |

所以本仓库自研的是**控制面**（信令、凭据、配额、观测），数据面**交给 coturn**：

```
                 ┌──────────────────────────────┐
   客户端 ──────►│  SecRelay-Relay（本仓库）      │  控制面
                 │  · 信令 WebSocket             │
                 │  · /api/v1/ice 凭据签发        │
                 │  · 配额 / 限速 / KPI          │
                 └───────────┬──────────────────┘
                             │ 签发短期凭据
                             ▼
                 ┌──────────────────────────────┐
   客户端 ──────►│  coturn（外部部署，非本仓库）  │  数据面：只转发密文
                 │  UDP 端口池 + TCP/443 回退     │
                 └──────────────────────────────┘
```

## 4. 防滥用：无账号前提下的保护

**这是本仓库最容易被低估的部分。** 一句"随便连"很容易变成"随便白嫖"——中继的唯一显著成本是带宽，而 1080p 中继约 **1.8 GB/小时**（单向），云出口价差可达 8 倍。

设计原则：**不要账号，但要有门槛、有配额、有观测。**

| 层级 | 措施 | 作用 | 绕过难度 |
|---|---|---|---|
| L1 | **短期凭据**（TURN REST API 风格：`username = 过期时间戳`，`credential = base64(HMAC-SHA1(secret, username))`） | 挡住直接用公开 TURN 配置白嫖 | 低（自己能调 `/api/v1/ice` 拿） |
| L2 | **每 IP 并发连接上限** | 挡住单机开大量会话 | 中 |
| L3 | **每 IP 日流量配额** | 挡住持续大量转发 | 中（换 IP 可绕） |
| L4 | **TCP/443 回退** | 不是防护，是可用性：穿透企业防火墙 | — |
| L5 | **黑名单 + 异常检测**（如单 IP 长时间满载） | 兜住自动化滥用 | — |
| L6 | **可选 Proof-of-Work**（未实现，预留） | 抬高批量滥用的成本 | 高 |

> **必须对用户诚实**：L1~L3 只能挡住"顺手白嫖"，挡不住有决心的攻击者。
> 如果哪天中继账单失控，唯一的根本解是**把凭据与账号体系绑定**（而那与"不做账号验证"冲突）。
> 因此本服务预留了匿名 `subject` 字段（见 §8），让这条演进路径不必推翻现有客户端。

### 流量口径

服务端**只统计转发字节数**，不做内容检查——否则就破坏零知识了。KPI 埋点尽量放在"量"上，不放在"内容"上。

## 5. 信令协议（v0 草案）

端点为 WebSocket `/ws/signal`。**无鉴权**，连接即可用。

匿名身份：客户端自己生成 `peer_id`（随机 UUID），服务端**不持久化**、不校验、重启即忘。

| 消息 | 方向 | 说明 |
|---|---|---|
| `hello` | C→S | 声明 `peer_id`、协议版本、能力位 |
| `create` | C→S | 创建一个会话，返回 `session_id`（短码） |
| `join` | C→S | 用 `session_id` 加入 |
| `offer` / `answer` | C↔S↔C | 透传 SDP |
| `candidate` | C↔S↔C | 透传 ICE 候选 |
| `bye` | C→S | 主动离开 |
| `error` | S→C | 错误码 + 说明 |

生命周期：会话在**双方都在线**时有效；任一断开或超时（默认 120s 无活动）即销毁。**信令内容不落盘。**

> `offer`/`answer` 里包含 IP 候选，属于**元数据**。中继不解密媒体，但会看到候选地址——
> 这一点要在隐私说明里写清楚，不要宣称"服务器什么都不知道"。

## 6. 零知识如何成立

| 数据 | 是否经过中继 | 中继能否读取 |
|---|---|---|
| 屏幕 / 摄像头 / 麦克风 | 打洞失败时经过 | ❌ DTLS-SRTP 加密；若启用 SFrame 端到端，连媒体服务器也不可读 |
| 文件 | 打洞失败时经过 | ❌ 端到端加密的 QUIC 流 |
| 消息 | 通常不经过（走设备直连或账号系统的密文暂存） | ❌ |
| 信令内容（SDP/候选） | ✅ 经过 | ⚠️ **能读到 IP 候选**（元数据） |
| 流量大小与时刻 | — | ⚠️ **元数据**（不可避免） |

**结论**：中继在密码学上读不到内容，但会掌握连接元数据。文案要精确，不要过度承诺。

## 7. 部署要点

- **多区域 + DNS 加权**：让客户端就近选点；直连成功率与延迟都受益。
- **UDP 端口池**：coturn 需要一段可用的 UDP 端口范围（如 `49152-65535`），防火墙必须放行。
- **TCP/443 回退必开**：企业 WiFi 常封 UDP，这是可用性底线。
- **TLS/DTLS 证书**：用真实证书，别自签。
- **建在带宽便宜的地方**：成本几乎全在出口带宽，不在服务器规格。"换更大的服务器"不是成本杠杆。
- **IPv6 优先**：IPv6 直连概率显著更高，是零成本的中继占比杠杆。

### 容量粗算（用于预算，不是承诺）

| 场景 | 单路码率 | 中继流量（单向） | 1000 路·小时 |
|---|---|---|---|
| 720p30 | 2 Mbps | ≈ 0.9 GB/h | ≈ 0.9 TB |
| 1080p30 桌面文字 | 4 Mbps | ≈ 1.8 GB/h | ≈ 1.8 TB |
| 1080p60 准无损 | 12 Mbps | ≈ 5.4 GB/h | ≈ 5.4 TB |

> 目标：**中继占比 < 15%**。每降低 10 个百分点，中继账单约降 40%。

## 8. 与 SECTL-auth 的边界

**中继不依赖账号系统，也不校验它。** 即使 SECTL-auth 完全宕机，SecRelay 的 P2P 与中继路径依然可用。

为了将来可能给配额绑定账号而不推翻客户端，协议里**预留**匿名主体字段：

```jsonc
// /api/v1/ice 请求体（可选字段，现在忽略）
{
  "subject": "anon:<random-uuid>",  // 匿名主体；登录后可由客户端填 user_id
  "client_version": "0.1.0",
  "platform": "windows"
}
```

现在服务端只把它当作**配额分组键**使用（不校验真实性、不调用 SECTL-auth）。将来若要启用校验，
只是把这个字段从"信任"改为"验证"，**客户端协议不变**。

## 9. 观测与 KPI

从第一天就要埋点，否则成本失控时无法定位。

| 指标 | 为什么重要 | 目标 |
|---|---|---|
| **直连成功率** | 中继占比的分母 | > 80% |
| **中继占比** | 唯一的成本杠杆 | **< 15%** |
| 打洞阶段耗时分布（p50/p95） | 影响连接体验 | p95 < 3s |
| 每 IP 连接数与流量 Top N | 滥用检测 | — |

| 信令错误码分布 | 协议与网络问题定位 | — |

## 10. 配置项

全部通过环境变量注入（`.env` 已在 `.gitignore` 中排除）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `BIND_ADDR` | `0.0.0.0:8080` | HTTP/WS 监听地址 |
| `PUBLIC_BASE_URL` | `http://127.0.0.1:8080` | 对外可访问的 HTTP(S) 基址，用于拼信令的 `wss://.../ws/signal`。反代/域名场景**必须**改，否则客户端拿到的是内网地址 |
| `TURN_SECRET` | （必填） | 与 coturn `static-auth-secret` 一致，用于签发短期凭据 |
| `TURN_URLS` | （必填） | 逗号分隔，如 `turn:relay.example.com:3478?transport=udp,turns:relay.example.com:5349` |
| `TURN_CREDENTIAL_TTL` | `600` | 短期凭据有效期（秒） |
| `TURN_REALM` | `secrelay.relay` | 必须与 coturn 的 `realm` 一致，会下发给客户端 |
| `TURN_CREDENTIAL_MODE` | `ephemeral` | `ephemeral`=签发短期凭据；`open`=完全开放（**不推荐，见 §4**） |
| `STUN_URLS` | （必填） | 逗号分隔的 STUN 地址 |
| `MAX_CONNS_PER_IP` | `16` | 每 IP 并发信令/中继会话上限 |
| `DAILY_BYTES_PER_IP` | `21474836480` | 每 IP 每日中继流量上限（20 GiB） |
| `SESSION_IDLE_TIMEOUT` | `120` | 信令会话空闲超时（秒） |
| `RUST_LOG` | `info` | 日志级别 |

### 接口

| 路由 | 鉴权 | 说明 |
|---|---|---|
| `GET /healthz` | 无 | 健康检查与配置自检 |
| `GET /metrics` | 无 | Prometheus 文本指标 |
| `GET\|POST /api/v1/ice` | 无 | STUN/TURN 配置（含短期凭据） |
| `GET /api/v1/relay` | 无 | **中继发现**：短 ID + 信令地址 + ICE 列表（TURN 带新签发凭据）+ TTL + realm |
| `GET /ws/signal` | 无 | 信令 WebSocket |

`GET /api/v1/relay` 是给客户端起步用的，未配置 TURN 时 `ice` 里只返回 STUN、不报错；
`turn_configured` 字段让客户端能判断中继路径是否可用。

## 11. 待定与风险

| # | 事项 | 说明 |
|---|---|---|
| R1 | **完全开放的中继会被白嫖** | §4 的措施只是门槛。若要根治必须绑定账号，与"不做账号验证"冲突——需要产品决策 |
| R2 | 配额状态存哪 | 单机内存（简单，无法多区域共享）vs Redis（可共享，多一个依赖）。当前骨架用内存 |
| R3 | 滥用时的处置流程 | 谁来发现、谁来封禁、多久解封 |
| R4 | 许可证 | 中继是网络服务，若担心被拿去搭闭源托管服务，应考虑 **AGPLv3**（见主仓库 D23） |
| R5 | 是否需要自建 STUN | 可以复用公网 STUN，但自建更可控 |
| R6 | coturn 编排与 IaC | 尚未落地 |
| R7 | 是否承担离线消息暂存 | 当前判定为**独立组件**，不放这里；若将来要放，需重新评估零知识与配额模型 |

### 中继短 ID

`GET /api/v1/relay` 返回的 `id` **不是中继自行声明的，而是由它的对外 origin 算出来的**：

```
canonical = scheme://host[:port]     // 全小写；去掉路径；省略默认端口（https:443 / http:80）
id        = base32(sha1(canonical))[0..10]     // RFC 4648 大写、无填充
```

输入取配置里的 `PUBLIC_BASE_URL`，**不用请求的 Host 头**（反代场景下 Host 不可信）。
客户端用同一规则自己算一次，与服务端上报的值比对，对不上就不认。

为什么不让中继自己声明：中继是开放且没有注册表的，自行声明就能冒用别人的 ID。
绑到 origin 之后，**冒用某个 ID 就必须真正拥有那个 origin**。

这里用 SHA-1 而不是 SHA-256：ID 是**标识**不是安全原语 —— 它防的是"冒用别人的 ID"，
而那要求攻击者真的控制那个 origin，与哈希的抗碰撞性无关。
